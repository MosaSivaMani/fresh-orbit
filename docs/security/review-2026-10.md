## 1. Summary

The basics are in good shape. JWT validation is strict and pinned to HS256. Refresh tokens rotate, and reuse revokes the
whole family. OTPs come from a CSPRNG and only their HMAC is stored. Every `/admin` endpoint carries a permission, and
customer data is scoped to the caller. All SQL is parameterised. Webhook signatures are compared in constant time. The
Fake gateway is refused in Production, and no real secrets have ever been committed. Both dependency scans are clean.

Two problems must be fixed before any public launch:

1. **OTP codes go to the logs in every environment (SEC-1).** The development SMS sender logs every message, including
   OTP codes. It is registered unconditionally, so in Production anyone who can read the logs can sign in as any customer.
2. **The rate limits break behind Caddy (SEC-2).** The API never reads `X-Forwarded-For`, so every request seems to come
   from the proxy's IP. The per-IP OTP and login limits then apply to the whole customer base at once (5 OTP calls per
   10 minutes for everyone). Adding forwarded headers without a trusted-proxy list would instead let attackers bypass
   every IP limit.

The Medium findings are about abuse resistance and data protection, not direct compromise. Three need a team decision:
SEC-4 (lockout model), SEC-8 (scope of DPDP erasure) and SEC-9 (who may change tax rates).

## 3. Verified as OK

These were checked in code and found correct. File references are the evidence.

### Authentication
- **JWT validation**: issuer, audience, signing key, lifetime and `ValidAlgorithms = [HS256]` are all set; clock skew is 30 s; `MapInboundClaims = false`; options are validated at start (`SharedKernel.Web/Auth/AuthenticationExtensions.cs:20-44`). Tokens carry `iat`, `nbf`, `exp` and `jti` (`AccessTokenFactory.cs:34-67`). There is no `none` algorithm path and no key from the token header.
- **Key source**: `Jwt:SigningKey` is empty in `appsettings.json`, so it must come from the environment or secrets; startup fails if it is missing (`[Required]`, `[MinLength(32)]`).
- **Refresh tokens**: 32 CSPRNG bytes, base64url, and only their SHA-256 is stored (`IdentityPorts.cs:76-78`). Rotation on every use (`RefreshToken.cs:62-69`). Presenting a rotated token revokes the active family and raises `RefreshTokenReuseDetected` (`TokenService.cs:46-56`). Refresh re-checks user status, staff `IsActive` and the customer link (`TokenService.cs:63-84`).
- **OTP**: 6 digits from `RandomNumberGenerator.GetInt32` (`IdentityPorts.cs:81-90`); stored as HMAC-SHA256 over challenge id and code (`IdentitySecurity.cs:13-19`); compared in constant time (`OtpChallenge.cs:77`); 5-minute lifetime; consumed on success; at most 5 attempts (`OtpChallenge.cs:65-85`). Parallel guesses race on `xmin` (`ModelConventions.cs:57-63`), so they cannot get past the attempt counter. Per-phone limits of 3 per 10 min and 10 per day, plus a 30 s resend gap (`OtpService.cs:156-178`).
- **Enumeration resistance**: OTP request returns the same answer for unknown, active and disabled phones (`OtpService.cs:93-99`). Staff login verifies a dummy hash for unknown emails (`StaffAuthService.cs:42-46`). SEC-4 is the exception, for locked accounts only.
- **Staff passwords**: ASP.NET Core Identity `PasswordHasher` (PBKDF2), rehashed on upgrade (`IdentitySecurity.cs:23-36`, `StaffAuthService.cs:68-71`). Policy: at least 12 characters, a common-password list, at least 4 distinct characters (`IdentityPorts.cs:94-111`). Changing the password requires the current one and revokes every session (`StaffAuthService.cs:86-99`). An admin reset revokes sessions (`StaffService.cs:90`).
- **Logout**: revokes only a token that belongs to the caller (`TokenService.cs:97-104`); `allDevices` revokes every token of the user.
- **Account deletion and block**: anonymises the user (phone, email and password hash set to null; DISABLED) and revokes sessions (`IdentityApi.cs:85-105`). A deleted account cannot be re-enabled (`User.cs:120-125`).

### Authorization
- **Every `/admin` endpoint requires a permission**, either per endpoint or on its group. Counted per file: Catalog 17/17, Locations 23/23, Inventory 14/14, Pricing 9/9, Payments 19/19; Delivery, Settings, Notifications, Reporting, Audit and Staff/Roles set it on the group. `/admin/auth/*` uses `RequireStaff`. A customer token has no `perm` claims, so it gets 403.
- **Customer endpoints** use `RequireClaim(typ, CUSTOMER)` on `/me` (Customers, Notifications) and on `/auth/logout`.
- **BOLA / IDOR**: payments and refunds load the order and compare `CustomerId` with the caller, returning 404 when it does not match (`OnlinePaymentService.cs:87-96`). Addresses are always loaded by `(customerId, addressId)` (`AddressService.cs:182-186`). On `integration/phase3`, orders are loaded through `CustomerOf(actor)`, and a staff token on customer order routes gets `LOGIN_REQUIRED`.
- **Location scoping (staff)**: Payments (`LocationGuard.EnsureAccess` in `RefundService.cs:36-40,76-81`, and in reads), Pricing (`PricingService.cs:25-162`, `BulkPriceService.cs:149`), Delivery (`Ports.cs:55-73`), Inventory (`InventoryReads.cs:185-229`), Reporting (`ReportRequests.cs:74-92`) and Locations list filtering (`LocationsEndpoints.cs:121,179`).
- **Mass assignment**: requests are explicit `sealed record`s with no owner, status, price or version fields (for example `UpdateProfileRequest`, `SaveAddressRequest`, `CreateRefundRequest`). On `integration/phase3`, `CheckoutRequest` has no lines or prices, only `ExpectedTotalPaise`, which is compared against the server total.
- **Separation of duties**: a refund's requester cannot approve it (`Payment.cs:524`), and whoever recorded a cash-settlement difference cannot settle it (`CashSettlement.cs:117`).

### Input and injection
- **SQL**: all raw SQL is either an EF interpolated `FromSql`/`ExecuteSqlAsync` (parameterised) or an `NpgsqlCommand` with parameters (`StorefrontReads.cs`, `ReportReader.cs`). `ORDER BY` columns come from an allow-list (`ReportReader.cs:429-436`, `StorefrontReads.cs:374`). Report filters must be UUIDs or UPPER_SNAKE codes (`ReportReader.cs:438-450`). The sample purger checks table names against a pattern (`SampleDataPurger.cs:27-31`). Search terms go into `to_tsquery` only as a bound parameter, after regex tokenisation.
- **Storage keys**: segments may contain only `[a-z0-9-_.]`, may not start with a dot, and the resolved path must stay under the root (`StorageKeys.cs`, `LocalDiskFileStorage.cs:143-150`). Keys are generated from server ids, never from file names.
- **Image upload**: type is checked by magic bytes, not by name; a 5 MB streaming cap; renditions are re-encoded to WebP with EXIF removed (`Images.cs:35-55,129-145`, `SkiaImageProcessor.cs`). The size gap is SEC-5.
- **Notification templates**: one regex pass replaces `{{name}}`, with no evaluation or recursion (`Template.cs:100-127`). Email bodies are `text/plain` (`Senders.cs:73`), so values cannot inject HTML or scripts.
- **CSV**: cells containing `, " CR LF` are quoted with doubled quotes, and formula prefixes are neutralised (SEC-14 covers the gaps). Exports are capped at 100,000 rows.

### Business logic and payments
- **Webhook signature**: HMAC-SHA256 over the raw body, hex-decoded and checked for length, compared with `FixedTimeEquals` (`FakePaymentProvider.cs:226-242`). A missing secret means rejection. Replay is blocked by a unique `(provider, providerEventId)` constraint plus an existence check, retried on races (`WebhookService.cs:59-79`). The captured amount and currency must match, otherwise an `AMOUNT_MISMATCH` issue opens and the payment stays PENDING (`PaymentEventApplier.cs:58-69`). The Fake format has no timestamp, so no replay window is needed. Real adapters must keep the provider's own replay protection.
- **Fake provider**: startup fails if `Payments:Providers:FAKE:Enabled` is set in Production (`ProviderCatalog.cs:35-53`, `ValidateOnStart`). The `/dev/payments/fake/*/simulate` endpoint is mapped only in Development or Testing (`PaymentsModule.cs:90-94`).
- **Refunds**: the refundable amount is checked inside the Payment aggregate (`Payment.cs:343`). The Payment row version (`xmin`) plus `SaveRetry` stops two refunds together from exceeding what was paid (`RefundService.cs:25-49`). Approve, reject and mark-paid require `If-Match`.
- **Idempotency**: scope is method + route template + caller user id, so keys never replay across users. The request hash covers method, path, query and body. The key length is capped at 100. A 5xx releases the key (`IdempotencyFilter.cs:42-134`). All `Idempotency-Key`-required routes in §1.8 on `main` use `WithIdempotency(required: true)`.
- **Delivery code**: 4 digits from a CSPRNG (`Shipment.cs:339-340`), locked after 5 wrong codes (`Shipment.cs:55,121`), shown only while OUT_FOR_DELIVERY (`DeliveryApi.cs:76`).
- **Sample data**: refused in Production (`MigrationRunner.cs:12`).

### Data, configuration and transport
- **Secrets in git**: `git log --all -p` was searched for signing keys, webhook secrets, passwords, AWS and Razorpay key patterns, private keys and `.env` files. Found only the documented local development values (`freshorbit_dev`, `dev-only-signing-key-change-me-…`, test-only secrets in tests). `.env` and `.env.*` are git-ignored.
- **Problem Details**: a 500 returns a fixed message and code `INTERNAL_ERROR` with no exception text; the exception is logged server-side only (`FreshOrbitExceptionHandler.cs:22-25,49`). EF `EnableSensitiveDataLogging` and `EnableDetailedErrors` are not used anywhere.
- **Request logging**: Serilog request logging records the path, not the query string or bodies. Apart from the SMS and email dev senders (SEC-1, SEC-17), no log template contains phone numbers, tokens or codes.
- **CORS**: an explicit origin list from configuration, empty by default, with no `AllowCredentials`. That is correct for bearer tokens. Exposed headers are limited to `ETag`, `Location`, `Idempotent-Replayed` and `Retry-After`.
- **OpenAPI and Scalar**: mapped only when `IsDevelopment()` (`Program.cs:35-39`).
- **Health**: `/health` returns only the status text (default writer), with no dependency details.
- **Payment data**: no card data or provider secrets are stored. Only provider order, payment and refund ids, the method and the amount (`Payment.cs`). Webhook headers are reduced to signature and event-id headers before storage (`WebhookService.cs:150-156`).

## 5. India-specific notes (DPDP Act 2023, RBI)

- **Notice and consent**: OTP sign-up collects the phone number only; email and name are optional. Marketing is opt-in (`Customer.MarketingOptIn`, default false). The consent notice text belongs in the front ends (out of scope here).
- **Erasure (s.12)**: implemented for the profile, active addresses and the user record. Gaps are SEC-8 (inactive addresses) and SEC-13 (OTP challenges, outbox, webhook payloads). Data kept for tax law (invoices, order snapshots, GST) should be listed as a legal-retention exception in `docs/product/customers.md`.
- **Breach readiness (s.8(6))**: needs the audit trail (SEC-7) and log hygiene (SEC-1).
- **Payment data**: RBI card-storage rules are met by design. No card data or PAN is ever handled, only gateway tokens and ids. Keep it that way when the Razorpay adapter is added: never log or store `card.*` objects from webhook payloads.
- **SMS**: TRAI DLT template ids are carried (`SmsMessage.DltTemplateId`), and the real sender must use them (SEC-1).
